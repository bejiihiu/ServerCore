# Протокол WebSocket

**Языки:** [English](../websocket-protocol.md) | Русский

WebSocket-канал — единственный транспорт между backend и плагином Minecraft. HTTP-фолбэка нет и не
планируется. Инициатор соединения всегда плагин; backend — шлюз.

## Транспорт и безопасность

- **Только WSS.** Соединения идут по TLS; апгрейд в открытом виде отклоняется.
- **Секрет на каждый сервер.** У каждого зарегистрированного сервера Minecraft свой HMAC-секрет,
  настроенный одинаково на обеих сторонах.
- **Аутентификация на хендшейке.** Авторизация соединения происходит **до апгрейда**: плагин добавляет к
  запросу апгрейда `?server=<id>&ts=<ms>&nonce=<n>&sig=<hmac>`, и backend проверяет HMAC по
  `server|ts|nonce` ещё до того, как сокет появится. Устаревший timestamp или повторно использованный
  nonce отклоняются сразу. Legacy-кадры `SERVER_HELLO` после апгрейда не принимаются.
- **Подпись сообщений.** Каждый кадр в обе стороны несёт HMAC-подпись, посчитанную по каноническому json
  конверта (id, type, timestamp, payload) без поля hmac.
- **Защита от повторов.** Timestamps должны попадать в окно допуска; id конвертов отслеживаются, а
  дубликаты повторно подтверждаются, но никогда не обрабатываются заново.
- **Валидация схемы.** Каждое входящее сообщение валидируется по схеме своего типа — Zod на backend,
  типизированные DTO с kotlinx.serialization в плагине. Тип, которого старая сборка не знает,
  декодируется в сырой passthrough, а не роняет соединение. Обе стороны дополнительно тестируются против
  общего контракта полей в `protocol/messages.json` (см. [Изменение протокола](#изменение-протокола)).
- **Ограничение размера.** Слишком большие кадры отклоняются сразу (`WS_MAX_PACKET_BYTES`, по умолчанию
  262144).

## Конверт сообщения

У каждого сообщения в обе стороны один и тот же конверт:

```text
{
  id: string            // unique message id
  type: string          // one of the message types below
  timestamp: number     // epoch millis, sender clock
  correlationId?: string // set when the message answers an earlier one
  payload: <T>          // type-specific body, validated by schema
  hmac: string          // hmac-sha256 over the canonical json of the frame minus the hmac field
}
```

`hmac` считается по **каноническому json** конверта без поля hmac: ключи объектов отсортированы
рекурсивно на каждом уровне, компактные разделители — ровно то, что хешируют обе реализации.
`correlationId` связывает ответ с запросом, который его вызвал: результаты проверки сессии отвечают
конкретным пробам.

В каноническом json нет представления для значений, из-за которых одна подпись накрыла бы два разных
payload'а: неконечные числа (сырой литерал `1e400` парсится в `Infinity`, а он хешируется так же, как
`null`) и абсурдная глубина вложенности отклоняются, а кадр с ними считается невалидным — его не
подписывают и не проверяют.

## Типы сообщений

### Жизненный цикл и статус

| Тип | Направление | Назначение |
|---|---|---|
| `SERVER_STATUS` | plugin → backend | Регистрация и пуши статуса; несёт `onlinePlayers`/`maxPlayers`, опциональные `tps`, `version` и ops-состояние `state` — `STARTING`, `RUNNING`, `RESTARTING`, `STOPPING`, `OFFLINE`, `UPDATE_READY`. Опциональное `activeSpecSessions` берётся из собственного реестра spec плагина и показывается админам в `/stats`; опциональное `telegramSuppressed` сообщает backend, что Telegram-модуль самого FlectonePulse прямо сейчас делает анонс, и бот молчит по этому событию |
| `SERVER_HEARTBEAT` | plugin → backend | Периодический признак живости и снимок метрик; несёт опциональное `activeSpecSessions`. Heartbeat'ы намеренно ждут ACK — ack служит плагину сигналом живости на стороне чтения |
| `NETWORK_SNAPSHOT` | backend → plugin | Агрегат всех игровых серверов, известных шлюзу: общее число игроков плюс по строке на сервер с его нагрузкой и возрастом heartbeat'а на момент генерации. Уходит всем серверам сразу после того, как heartbeat обновил справочник (не чаще одного пуша в секунду), поэтому игровой бар сети никогда не опрашивает сервер. См. [инфо-бары сервера](bars.md#бар-сети) |
| `SERVER_READY` | backend → plugin | Подтверждение регистрации с ожидаемой частотой heartbeat'ов (`heartbeatIntervalMs`, `heartbeatTimeoutMs`). Тип описан в протоколе, но **пока не отправляется** — сегодня роль сигнала «ты зарегистрирован» играет ack регистрационного `SERVER_STATUS` |

### Присутствие игроков

| Тип | Направление | Назначение |
|---|---|---|
| `PLAYER_JOINED` | plugin → backend | Сессия началась; запускает проверки аккаунта и, если нужно, запрос авторизации |
| `PLAYER_LEFT` | plugin → backend | Сессия закончилась; ожидающие запросы авторизации для неё отменяются |

### Аутентификация

| Тип | Направление | Назначение |
|---|---|---|
| `AUTH_REQUEST` | backend → plugin | Backend просит плагин придержать сессию до подтверждения в Telegram |
| `AUTH_APPROVED` | backend → plugin | Подтверждение получено; плагин возвращает игрока в обычную игру |
| `AUTH_REJECTED` | backend → plugin | В подтверждении отказано; сессия остаётся заблокированной |
| `AUTH_EXPIRED` | backend → plugin | TTL токена истёк без решения |

### Гостевой режим

| Тип | Направление | Назначение |
|---|---|---|
| `GUEST_STARTED` | plugin → backend | Гостевая сессия создана, снапшот сохранён |
| `GUEST_ENDED` | plugin → backend | Гостевая сессия завершена (авторизовался либо вышел, снапшот сохранён) |

### Приём и аккаунт

| Тип | Направление | Назначение |
|---|---|---|
| `APPLICATION_SUBMITTED` | backend → plugin | Заявка ушла на голосование (информационно; используется в игровых плейсхолдерах) |
| `APPLICATION_APPROVED` | backend → plugin | Заявка принята; аккаунт может стать ACTIVE |
| `APPLICATION_REJECTED` | backend → plugin | Заявка отклонена |
| `APPLICATION_EXPIRED` | backend → plugin | Окно голосования закрылось без кворума после единственного автопродления |
| `ACCOUNT_DELETED` | backend → plugin | Аккаунт удалён; любую живую сессию нужно завершить |
| `LINK_TOKEN` | backend → plugin | Свежий одноразовый deep-link токен для вошедшего игрока; игровой чат показывает личную ссылку на бота |
| `SESSION_CHECK` | backend → plugin | Проба владения: этот UUID сейчас в игре? |
| `SESSION_CHECK_RESULT` | plugin → backend | Ответ на пробу с состоянием живой сессии |

### Администрирование

| Тип | Направление | Назначение |
|---|---|---|
| `SPEC_STARTED` | plugin → backend | Сессия наблюдения началась; backend записывает её в `audit_logs` (`kind: "spec"`). Payload: `adminUuid`, `targetUuid`, опциональные `sessionId`, `adminUsername`, `targetUsername`. |
| `SPEC_ENDED` | plugin → backend | Наблюдение завершено; backend закрывает аудит-трейл с `durationSec` и `reason` (`NORMAL`, `FORCED`, `TARGET_DISCONNECTED`, `ADMIN_DISCONNECTED`, `ERROR`). |

### Локализация

| Тип | Направление | Назначение |
|---|---|---|
| `LOCALE_PUSH` | backend → plugin | Полное содержимое одного файла локали (`ru` или `en`); целиком заменяет копию плагина для этого языка |
| `LOCALE_ACK` | plugin → backend | Результат применённого пуша; связывается с пушем через `correlationId` |

Payload `LOCALE_PUSH`:

```text
{
  locale: string     // language tag; the plugin bundles and accepts "ru" and "en"
  revision: string   // opaque backend-side revision id (commit sha or hash)
  content: string    // the FULL yaml file, never a diff
}
```

Payload `LOCALE_ACK`:

```text
{
  locale: string
  revision: string   // echoed from the push
  accepted: boolean
  reason?: string    // present when accepted is false
}
```

Семантика:

- Плагин никогда не скачивает файлы локали сам; HTTP-пути нет. Backend везёт эталонный бандл в своём
  образе и отправляет его каждому подключённому серверу.
- Пуши **целиком файл**: плагин заменяет всё своё хранилище локали для этого языка. Частичные слияния
  не делаются.
- Плагин валидирует payload (yaml парсится, локаль есть среди вшитых, хранилище непустое), а затем
  атомарно подменяет живое хранилище; отклонённый пуш оставляет работающую локаль нетронутой, и о нём
  сообщается обратно с `reason`.
- При успехе плагин сохраняет файл в свою папку данных; на старте сохранённый файл важнее вшитого
  семени, поэтому состояние локали переживает рестарты. Revision не сохраняется между рестартами
  плагина — следующее соединение снова получает текущий бандл.
- Повторная доставка того же `revision` безопасна: плагин заново парсит и идемпотентно применяет его.

Семантика пуша:

- Backend загружает эталонный бандл один раз при старте (отсутствующий или пустой бандл роняет старт;
  слишком большой отклоняется до того, как превратится в недоставляемый кадр). `revision` выводится из
  содержимого: первые 16 hex-символов его sha256 — так что неизменённый файл всегда пушится с тем же id.
- Сейчас backend отдаёт только `ru`. Плагин также вшивает `en` как базовый слой, и его обработчик пуша
  принимает `en` так же, поэтому отдача второй локали позже — изменение на стороне backend без правок
  протокола.
- Каждое свежее соединение получает один `LOCALE_PUSH` сразу после того, как подтверждён регистрационный
  `SERVER_STATUS`. Для последующих кадров статуса на том же сокете пуш не повторяется; переподключение —
  новый сокет, и он получает свежий пуш.
- `LOCALE_ACK` отслеживается по id сервера. Backend различает применённый бандл, отказ (с причиной от
  плагина) и ack на ревизию, которую этот процесс уже не отдаёт. Пропавший ack на том же соединении не
  ретраится — следующая регистрация доставит текущую ревизию заново.
- Старые плагины без обработчика `LOCALE_PUSH` просто никогда не отвечают ack: пуш остаётся
  неподтверждённым на этом соединении, и следующая регистрация доставляет его снова. Старый backend
  вообще не отправляет этот кадр, а новый безвреден для сборки, которая не знает типа.

## Изменение протокола

`protocol/messages.json` — машиночитаемый контракт для каждого типа в проводе, и обе стороны
тестируются против него. Одна запись на тип несёт:

- `type` — имя в проводе
- `direction` — `plugin_to_backend`, `backend_to_plugin` или `both`
- `fields[]` — контракт payload'а: `uuid` / `objectId` / `string` / `integer` / `number` / `boolean` /
  `enum` (со `values`) / `object` (с вложенными `fields`), у каждого отмечено `required` или нет
- `example` — один полный payload, валидный по схеме
- `pluginTransport` (`typed` / `raw` / `absent`) и, если слой ws его декодирует, `pluginDto`

Два набора тестов сверяются с этим файлом:

- `backend/tests/protocol-contract.test.ts` обходит zod-схемы: у каждого типа из манифеста есть схема
  payload'а и каждая схема есть в манифесте, имена полей, обязательность, типы и значения enum совпадают
  в обе стороны, `BACKEND_TO_PLUGIN_TYPES` соответствует объявленным направлениям, и каждый пример
  валидируется.
- `plugin/src/test/kotlin/kz/bejiihiu/servercore/websocket/ProtocolContractTest.kt` проверяет сторону
  kotlinx: `MessageType` перечисляет ровно те типы, что переносятся, каждая ветка типизированного
  payload'а парсит свой пример и заново выдаёт все обязательные поля, каждый сырой тип декодируется в
  `Payload.Raw` с целым именем в проводе, и каждый ws DTO объявляет поля манифеста с той же
  опциональностью и парсит пример.

**Добавление или изменение сообщения — это одна правка в четырёх местах:** запись в манифесте,
zod-схема на backend (плюс `MESSAGE_TYPES` / `BACKEND_TO_PLUGIN_TYPES`), `MessageType` и payload (или DTO)
в плагине и любой обработчик. `bun test` и `./gradlew :plugin:test` роняют сборку при расхождении:
переименованное или удалённое обязательное поле, переворот required↔optional, смена направления,
значение enum, которого не знает другая сторона, тип или поле, отсутствующее на одной из сторон, или
пример, который больше не парсится. Типы с `status: "reserved"` описаны, но в проводе их нет; плагин
намеренно их не несёт.

## Хендшейк

```text
plugin                              backend
  | --- WS connect (WSS) -----------> |
  |      /ws?server=<id>&ts=<ms>&nonce=<n>&sig=<hmac>
  |                                  verifies hmac over server|ts|nonce
  |                                  BEFORE upgrade (replay-guarded nonce)
  | <--- 101 upgrade accepted ------- |   socket now exists
  | --- SERVER_STATUS (register) ---> |  identity + current load + ops state
  | <--- ACK ------------------------ |
  | <--- LOCALE_PUSH ---------------- |  full canonical bundle (fresh socket only)
  | --- LOCALE_ACK -----------------> |  applied / rejected + reason
  | --- SERVER_HEARTBEAT (periodic) ->|  acked by the backend
  | <--- NETWORK_SNAPSHOT ----------- |  aggregate of every known server (throttled to 1/s)
```

В хендшейке нет hello внутри канала: подпись в query-string и есть вся аутентификация, а кадр
`SERVER_HELLO`, пришедший после апгрейда, отклоняется как попытка даунгрейда. `SERVER_READY` в протоколе
есть, но пока не отправляется; фактический сигнал регистрации — ack регистрационного `SERVER_STATUS`.

Пока соединение не прошло пред-апгрейдный хендшейк, backend даже не создаёт сокет — окна для
неаутентифицированных кадров просто нет.

## Heartbeat и живость

- Плагин отправляет `SERVER_HEARTBEAT` с фиксированной частотой (по умолчанию раз в 15 с) и ждёт ack на
  каждый.
- Backend отслеживает время последнего кадра на соединение и помечает зависшие серверы.
- Каждый heartbeat также обновляет сетевой справочник; получившийся агрегат `NETWORK_SNAPSHOT` уходит
  всем подключённым игровым серверам, так что игровой бар сети показывает весь флот без опроса. Пуши
  троттлятся до одного в секунду — это схлопывает флот, у которого heartbeat'ы приходятся на одну
  секунду.
- Плагин делает зеркальную проверку: если на «подключённом» сокете нет входящих кадров
  `backend.liveness-timeout-milliseconds`, канал считается полуоткрытым и переподключение форсируется.

## Семантика переподключения

Разрывы ожидаемы, и обе стороны их обрабатывают:

1. Плагин переподключается с **экспоненциальной задержкой**, начиная с
   `backend.reconnect.initial-delay-seconds` и упираясь в `backend.reconnect.max-delay-seconds`.
2. После успешного переподключения плагин заново проходит хендшейк и **сверяет состояние** — живые
   сессии объявляются повторно, чтобы обе стороны видели одну и ту же реальность.
3. События классифицируются по надёжности: heartbeat'ы и ack устаревают по определению и при сбое
   выбрасываются; события присутствия, статуса и spec копятся в памяти; кадры жизненного цикла гостей
   (со снапшотами) **надёжные** и лежат на диске в ограниченной очереди (`backend.outbox-max-entries`),
   воспроизводясь после возврата связи с сохранением порядка.
4. Повторная доставка безопасна с обеих сторон: плагин помнит обработанные пуши backend в течение
   `backend.dedupe-ttl-milliseconds` и подтверждает дубликаты, но игнорирует их; backend повторно
   подтверждает воспроизведённые кадры, не обрабатывая их заново.

## Поведение при отказах

Упавший backend никогда не должен молча выдавать доступ:

- **Новые входы fail-closed.** Без живого backend никто не проходит аутентификацию; сервер не одобряет
  автоматически.
- **Короткие сбои не выкидывают игроков.** Уже авторизованные игроки продолжают играть через короткие
  простои.
- **Гостевой режим продолжает работать.** Гостевые сессии и ограничения действуют локально и переживают
  простой.
- **Ничего не теряется.** События, возникшие в офлайне, ждут в очереди исходящих; критичное состояние
  живёт в MongoDB, а не в памяти.

То же поведение действует на уровень ниже, когда backend жив, а MongoDB нет:

- `ACK` означает *получено*, а не *обработано*. Если обработке кадра нужна база и запись не удалась,
  backend отвечает на этот ack кадром `ERROR { code: "HANDLER_FAILED", inReplyTo: <frame id> }` по тому
  же соединению. Сокет остаётся открытым, последующие кадры обрабатываются нормально — сбой базы никогда
  не стоит игровому серверу связи.
- Упавший кадр backend не ретраит; решение о повторе принадлежит плагину (следующий пункт). Собственные
  припаркованные пуши backend (приглашения и вердикты авторизации, link-токены) уходят на следующем
  свипе, когда база вернётся.
- Ретрай — за плагином. Коррелированный `ERROR` значит, что кадр *не применён*, поэтому кадр `QUEUE` или
  `DURABLE` возвращается в парковку и отправляется заново с небольшой задержкой. Повторная отправка несёт
  новый id конверта и timestamp — переиспользованный id был бы лишь повторно подтверждён как дубликат, и
  обработчик больше никогда бы не выполнился, — поэтому каждый обработчик обязан переживать обработку
  одного события дважды. Повторов не больше трёх; дальше кадр логируется на уровне warn и отбрасывается,
  а счётчик отброшенных увеличивается. Fire-and-forget кадры (heartbeat'ы, статус) только логируются, а
  детерминированные сбои вроде `BAD_PAYLOAD` не ретраятся вовсе. `ERROR` без `inReplyTo` логируется и
  игнорируется.

### Идемпотентность обработчиков

Id конвертов дедупят *повторную доставку одного кадра*, а не *ретраи одного события*: ретрай по
дизайну — совершенно новый кадр. Поэтому инвариант формулируется на событие, а не на кадр: **обработчик
обязан прийти к одному и тому же состоянию, выполнившись один раз или трижды для одной идентичности
события**, где идентичность — то, что payload делает устоявшимся состоянием:

| Событие | Идентичность | Как поглощается повтор |
|---|---|---|
| `SPEC_STARTED` / `SPEC_ENDED` | `sessionId` | у строки аудита детерминированный id (`spec:<sessionId>:STARTED` / `...:ENDED`) и insert-only upsert, поэтому вторая доставка попадает в строку, созданную первой. Строки аудита остаются append-only: повторный end никогда не перезаписывает причину, записанную первым |
| `GUEST_STARTED` | `sessionId` | строка сессии создаётся insert-only на каждую открытую сессию, а upsert снапшота идёт с `$setOnInsert`, поэтому реплей подтверждает существующий снимок, а не сдвигает его |
| `GUEST_ENDED` | `sessionId` | закрытие уже закрытой сессии и удаление уже удалённого снапшота — no-op; `AUTHENTICATED` повторно ставит тот же статус |
| `PLAYER_JOINED` / `PLAYER_LEFT` | открытая сессия на uuid | строка аккаунта ищется или создаётся, link-токен ограничен одним на окно, а учёт сессий идёт по схеме «закрыть, затем создать»; устоявшийся вход воспроизводим только через путь припаркованного кадра, который сохраняет id конверта |
| `SERVER_STATUS` / `SERVER_HEARTBEAT` | соединение + payload | вывод состояния последним писателем на те же значения, а хук смены состояния срабатывает только на реальном переключении |
| `SESSION_CHECK_RESULT` | `correlationId` | проба удаляется из карты ожидания при разрешении, поэтому поздний или повторный ответ отбрасывается; у кадра надёжность `DROP`, и он никогда не ретраится |
| `ACCOUNT_DELETED` (сторона плагина) | `minecraftUuid` | очистка кеша аккаунта, ожидающей привязки и ожидающего идемпотентны; повторный пуш kick/revoke не может уронить плагин |

Собственный журнал spec плагина следует тому же правилу: аудит-трейл дедупит по `(sessionId, event)` в
памяти, поэтому повторно объявленная живая сессия или повторный отчёт пишут одну jsonl-строку на событие,
никогда две.

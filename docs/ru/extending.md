# Расширение ServerCore

**Языки:** [English](../extending.md) | Русский

Эта страница — карта для правки кодовой базы: где живёт новая деталь, какие файлы ходят вместе и что
сборка откажется принимать. Предполагается, что вы прочитали [архитектуру](architecture.md) и базовые
правила в [CONTRIBUTING](../../CONTRIBUTING.md).

Три инварианта решают большую часть дизайна:

- **Только Folia.** Выбирайте планировщик, которому принадлежит ресурс — сущность, регион, глобальный или
  асинхронный — и никогда не предполагайте главный поток.
- **Один транспорт.** Трафик плагин ↔ backend — только кадры WebSocket. Никакого HTTP между ними.
- **Fail closed.** Когда проверку нельзя завершить, отказывайте. Опциональные интеграции деградируют с
  предупреждением, никогда — молчаливым разрешением.

Гейты, без которых работа не считается сделанной:

```bash
cd backend && bun run typecheck && bun test
./gradlew :plugin:build
```

`:plugin:build` прогоняет тесты плагина; набор backend запускает тесты репозиториев против
`mongodb-memory-server` (или `MONGODB_TEST_URI`, если он задан) и пропускает их с сообщением, когда
поднять mongod не удалось.

## 1. Новый модуль-фича в плагине

### Форма

Один пакет на фичу в `plugin/src/main/kotlin/kz/bejiihiu/servercore/<module>/`. Разделите код так, чтобы
логика решений не зависела от сервера:

- **швы (seams)** — небольшие интерфейсы, через которые говорит логика (`ViewStateApplier`,
  `ResyncExecutor`, `SpecWorld`, `BarMetric` — существующие примеры);
- **чистый код решений** — тестируемый без Folia и PacketEvents;
- **продакшн-реализация** — класс, который действительно трогает `Player`, пакеты или файловую систему;
- **клей планировщика** — единственное место, где вызываются `entityScheduler`, `regionScheduler`,
  `globalRegionScheduler` или `asyncScheduler`.

Это разделение не для красоты: большинство тестов плагина работают без сервера, и могут они это только
потому, что швы существуют.

### Паттерн installer'а

Связка при старте живёт в `boot/`, по одному `<Feature>Installer` на подсистему. Installer:

- принимает `PluginContext` (листовые сервисы: plugin, `io`, локаль, UI-тулкит) плюс те installer'ы, от
  которых зависит — никогда сам синглтон плагина;
- `install()`-ит свои объекты один раз, на пути включения. Проверяет флаг конфига и выходит сразу, если
  фича выключена;
- опционально `start()`-ит отложенную работу, которой нужно дождаться остального графа (регистрация
  листенеров, подключение транспорта, восстановление сессий);
- `stop()`-ит всё, что построил, переживая частичную установку и ничего не бросая. Отменяйте задачи до
  закрытия хранилищ и завершайтесь до `ctx.io.shutdown()`.

`PluginContext` несёт полный контракт; прочитайте его, прежде чем добавлять фазу.

### Куда цепляться

| Что нужно | Хук |
|---|---|
| Команда | `LifecycleEvents.COMMANDS` (см. `bars/BarCommands`, `boot/AdminCommandInstaller`) |
| Событие Bukkit | `pluginManager.registerEvents(..., plugin)`, MONITOR, если вы только наблюдаете |
| Реакция на уровне пакетов | листенер в `packet/` + шов `ViewStateApplier` или исполнитель `sync` |
| Кадр от backend | типизированный колбэк `GatewayListener` или сырой fan-out `onWireMessage` |
| Поверхность для игрока | `ui/`, и планировщик сущности на каждый кадр |
| Плейсхолдер | `placeholderapi/PlaceholderResolver`, питаемый кешем, а не чтением метрики |

### Порядок старта и завершения

`ServerCorePlugin.onEnable` — единственный видимый порядок:

```
flectonepulse -> ops -> config (boot blocker) -> gateway -> spec reporting
-> i18n -> integrations -> guest -> packet -> sync -> viewer -> observer
-> protection -> spec -> esp -> admin commands
-> guest.start -> ui -> bars -> gateway.start -> papi -> announce
```

Правила порядка, которые важны при вставке модуля:

- конфиг раньше всего, что читает настройки; плохой конфиг backend выключает плагин, а не поднимает его
  наполовину подключённым;
- i18n раньше любой поверхности для игрока — всё рендерится через неё;
- packet/sync раньше их потребителей (`viewer`, `observer`, `esp`, `spec`);
- транспорт (`gateway.start`) после поверхностей, которым он не нужен, чтобы дефект в баре или UI никогда
  не задерживал WebSocket-связь;
- `papi` последним, потому что он читает живые кеши.

`onDisable` — это **порядок зависимостей, а не обратный старту**: клиентские представления
восстанавливаются, пока конвейер пакетов ещё подключён, сессии разматываются раньше, чем уходит сервис
пакетов, а пул io переживает каждое хранилище, которое через него флашится. Ставьте свой `stop()` в
точку, где эти гарантии сохраняются, а не просто по зеркальному индексу.

### Чеклист Folia

- `Player`, `World`, `Entity`, `Inventory` — только планировщик сущности/региона.
- Глобальные счётчики и серверные задачи — глобальный региональный планировщик.
- Фоновая периодическая работа — асинхронный планировщик.
- Файловый и сетевой I/O — виртуальные потоки (`ctx.io`).
- Колбэки WebSocket никогда не трогают игровые объекты: получить → провалидировать → разрешить UUID →
  перейти в планировщик-владелец → выполнить.
- Задачи сущности отменяются, когда сущность исчезает; очистка в духе `forget(uuid)` не даёт
  per-player картам пережить сессию.

### Не забудьте

1. **Конфиг** — ключ в `plugin/src/main/resources/config.yml`, загружается в объекте `*Config` с вшитыми
   дефолтами и зажимом значений. `ConfigLoaderTest` проверяет, что каждый ключ, который читают
   загрузчики, есть во вшитом файле и что дефолты совпадают.
2. **Локаль** — видимый пользователю текст идёт через `locale/`, никогда не в строку Kotlin. Добавьте
   ключ и в `locales/ru.yml`, и в `locales/en.yml`; `MessagesResourcesTest` падает на одностороннем
   ключе.
3. **Права** — узкая нода на каждую возможность в `protection/Permissions`. Не переиспользуйте
   `servercore.admin` для действия, доступного игроку.
4. **Документация** — дополните нужную страницу в `docs/`, если поведение видно оператору.
5. **Тесты** — чистая логика против швов. Привязанные к серверу пути остаются тонкими и явно
   непротестированными, а не замоканными так, что тест врёт.

### Минимальный скелет

```kotlin
class WidgetInstaller(private val ctx: PluginContext) {
    private var service: WidgetService? = null

    fun install() {
        val config = WidgetConfig.load(ctx.plugin.config, ctx.logger)
        if (!config.enabled) return

        val service = WidgetService(config, ctx.locale, ctx.io)
        service.start()
        this.service = service
    }

    fun stop() {
        service?.stop()
        service = null
    }
}
```

Добавьте его в `onEnable` в точке, где его зависимости уже существуют, держите поле на плагине и
вызывайте `stop()` из `onDisable` в порядке зависимостей.

## 2. Новое сообщение в проводе

`protocol/messages.json` — **единственный межъязыковой контракт**. Zod-схемы backend, кодек плагина, оба
набора тестов и страница протокола синхронизированы с ним, поэтому сообщение — это одна правка во всех
этих местах, никогда — изменение только на backend или только в плагине.

### Запись в манифесте

```jsonc
{
  "type": "WIDGET_OPENED",
  "direction": "plugin_to_backend",       // | backend_to_plugin | both
  "status": "active",                     // | reserved (documented, not on the wire)
  "pluginTransport": "typed",             // | raw | absent
  "pluginDto": "WidgetOpenedPayload",     // when the plugin has a DTO
  "summary": "one sentence on what triggers it and what consumes it",
  "fields": [
    { "name": "minecraftUuid", "type": "uuid", "required": true },
    { "name": "reason", "type": "string", "required": false }
  ],
  "example": {
    "minecraftUuid": "0f4d2f3e-8a44-4c21-9d0e-3b1f2a4c5d60",
    "reason": "manual"
  }
}
```

Типы полей: `uuid`, `objectId`, `string`, `integer`, `number`, `boolean`, `enum` (с `values[]`), `object`
(с `fields[]`) и `array` (с `items`). `required: false` значит, что отправитель может опустить ключ;
другая сторона всё равно обязана пережить его отсутствие. `pluginTransport` говорит, как его несёт
плагин: `typed` (`MessageType` + ветка `Payload`), `raw` (известный тип, декодируется в `Payload.Raw` и
раздаётся через `GatewayListener.onWireMessage`) или `absent` (эта сборка плагина его вовсе не несёт).

### Сторона backend

1. Добавьте тип в `MESSAGE_TYPES` в `backend/src/websocket/protocol/message-types.ts`.
2. Добавьте Zod-схему в `payloadSchemas` там же. Входящие кадры уже валидируются схемой конверта;
   схема payload'а — вторая половина этой границы.
3. Если backend его пушит, добавьте тип в `BACKEND_TO_PLUGIN_TYPES` и в `NO_ACK_TYPES` только когда ACK
   ждать не нужно (кадры хендшейка, ack, error). Всё остальное подтверждается по получении.
4. Зарегистрируйте обработчик ровно один раз из `backend/src/websocket/handlers/wiring.ts` (или из
   функции `register*Handlers` модуля, которую вызывает `wiring.ts`). `HandlerRegistry` намеренно
   отклоняет вторую регистрацию.
5. Держите обработчики тонкими: валидируйте/нормализуйте, вызовите сервис, дайте отказу
   распространиться. Соединение отвечает на упавший обработчик кадром `ERROR` с `inReplyTo` и сохраняет
   сокет — не изображайте успех и не закрывайтесь.
6. Добавьте сообщение в `docs/websocket-protocol.md`.

### Сторона плагина

1. Добавьте константу `MessageType` в
   `plugin/src/main/kotlin/kz/bejiihiu/servercore/websocket/Protocol.kt`, если манифест не помечает тип
   как `absent`.
2. Для `typed`: добавьте ветку `Payload` и обе карты кодека (`payloadToJson` / `payloadFromJson`) в
   `websocket/Protocol.kt`. Домейн-payload'ы, которые слои `ws`/`locale` парсят как DTO, живут в
   `ws/WsProtocol.kt` или `locale/LocaleProtocol.kt`. Для `raw`: ничего кроме записи в enum —
   провалидированный JSON доходит до `GatewayListener.onWireMessage`, а парсит его модуль-владелец.
3. Когда манифест объявляет `pluginDto`, добавьте этот сериализатор в таблицу `dtoSerializers` в
   `ProtocolContractTest`; набор проверяет поля DTO и их опциональность против манифеста.
4. Исходящие кадры получают класс `Durability`: `DROP` (устаревает по определению), `QUEUE` (переживает
   сбой переподключения) или `DURABLE` (должен пережить рестарт плагина, паркуется в очередь исходящих).
   Всё, чего нет в списке, теряется вместе со связью.
5. Потребляйте его через узкий мост (листенер в `spec`/`sync` или отдельный маленький листенер), а не
   дотягиваясь до транспорта из модуля-фичи.

### Правила совместимости

- Неизвестные типы подтверждаются и игнорируются с обеих сторон — более новый пир никогда не должен
  убивать старого. Поэтому новые сообщения можно выпускать до апгрейда другой стороны.
- Добавляйте опциональные поля; никогда не переименовывайте, не меняйте тип и не удаляйте обязательное
  поле на месте. Ломающее изменение — это новый тип.
- Никогда не переиспользуйте имя типа для другого смысла и не переносите опубликованную запись
  `status: "reserved"` без связки на обеих сторонах.
- Поля `integer` — это `z.number().int()`; дробные числа живут в полях `number` с явными границами.
  Канонический JSON ограничивает вложенность 64 уровнями и отклоняет неконечные числа, поэтому никогда не
  отправляйте payload, который полагается на то или другое.
- Идемпотентность: ретрай может прийти под новым id конверта с тем же содержимым. Обработчики,
  ключующиеся на естественную идентичность (`sessionId`, `applicationId`, `(applicationId, voterUuid)`), —
  норма; детерминированные id аудита существуют именно для этого.

### Контрактные тесты

- `backend/tests/protocol-contract.test.ts` — манифест ↔ Zod-схема (поля, обязательность, типы, enum,
  массивы/объекты), наборы направлений и пример payload'а, который должен валидироваться.
- `plugin/src/test/.../websocket/ProtocolContractTest.kt` — манифест ↔ `MessageType`, пример,
  декодированный реальным кодеком, и повторно выданный payload, который всё ещё обязан нести каждое
  обязательное поле.
- `backend/tests/fuzz-protocol.test.ts` — тотальность и враждебный ввод.

Сначала добавьте запись в манифест и пример, потом добивайтесь зелёных наборов. Если набор падает,
сообщение не готово — не правьте тест, чтобы он принял расхождение.

## 3. Новый бар

Бары — самое дружелюбное к копипасте расширение, потому что всё завязано на `BarId`. Новый бар трогает
эти места по порядку:

1. **`bars/BarId.kt`** — добавьте запись enum с двумя нодами прав. Из неё выводятся `key`, `commandName`
   (`<key>bar`), `label` и ключ локали `titleKey` (`bars.<key>.title`).
2. **`protection/Permissions.kt`** — добавьте `servercore.bars.<key>` и `servercore.bars.<key>.other`.
3. **`bars/BarsConfig.kt`** — добавьте `<Key>BarConfig` (минимум `enabled`, плюс пороги или опции), поле
   в `BarsConfig`, ветку в `isEnabled`, блок загрузчика, читающий `bars.<key>.*` с вшитыми дефолтами, и
   сами дефолты как константы. Исчерпывающий `when` заставит вас это обработать.
4. **`plugin/src/main/resources/config.yml`** — добавьте секцию `bars.<key>`. Зажимайте и
   переупорядочивайте плохие значения в загрузчике; плохой конфиг бара не должен блокировать старт.
5. **Реализация `BarMetric`** — `bar`, `read(player)` (выполняется в планировщике сущности этого игрока,
   поэтому читать его позицию законно), `readGlobal()`, когда значение не зависит от игрока (именно это
   питает PlaceholderAPI при нуле включённых баров), `start`/`stop` для фонового сэмплера, `forget(uuid)`
   для per-player кешей.
6. **`boot/BarsInstaller.kt`** — добавьте метрику в список под её флагом конфига. Installer владеет
   хранилищем переключателей, рендерером и командами; метрика владеет только числом.
7. **Локаль** — `bars.<key>.title` и каждый плейсхолдер из `values` в обоих `locale/ru.yml` и
   `locale/en.yml`. Шаблон владеет текстом и единицей; метрика владеет числом.
8. **PlaceholderAPI** — в `bars/BarSnapshots.kt` исчерпывающий `when` по `valueKey`, поэтому бар не
   скомпилируется без ветки. Если он должен отдавать `%servercore_bar_<key>%`, добавьте ещё случай в
   резолвер и известный список в `placeholderapi/PlaceholderResolver.kt`. Резолвер читает отрендеренный
   снапшот, а не живую метрику.
9. **Тесты** — `BarMetricsTest` на математику чтения, `BarsConfigTest` на дефолты/зажим,
   `BarPresentationTest`, если форма шаблона новая, `BarCommandsTest` на форму команды. Обновите
   `docs/bars.md`.

Правила, которые фреймворк уже навязывает:

- один активный бар на поверхность (`bossbar` / `actionbar`) на игрока; переключение переиспользует тот
  же экземпляр боссбара;
- задача обновления выполняется в планировщике сущности игрока, и пакет отправляет только этот поток;
- нечитаемое или неконечное значение рендерится пустым, а не бросает исключение;
- переключатели сохраняются в `bars.json` по игроку и поверхности.

## 4. Новый модуль backend

### Форма

```
backend/src/modules/<name>/
  types.ts             # domain types + typed errors
  repository.ts        # ports over storage, no mongoose types
  repository-mongo.ts  # mongoose implementation of those ports
  <name>-service.ts    # business logic; constructor takes one deps object
  memory-store.ts      # optional in-memory port impl / test double
  bot-callbacks.ts     # optional telegram glue, kept out of the service
```

Модели живут в `backend/src/database/models/` и экспортируются из `index.ts`. Репозитории отображают
документы в простые сериализуемые записи — документ mongoose за пределы модуля не выходит.

### Правила

- **Сначала порты.** Сервис зависит от интерфейсов, никогда от mongoose или grammY. Кладите порт в
  `services/ports.ts`, только когда его потребляет другой модуль; иначе держите его внутри модуля.
- **Один объект deps.** Конструкторы сервисов принимают именованные зависимости, а не позиционные
  аргументы. Так связка читаемее, а тестовые двойники очевиднее.
- **Сервисы решают, обработчики переводят.** Обработчик WebSocket или колбэк бота валидирует/нормализует
  и вызывает метод сервиса; запросы он не выполняет.
- **Ошибки типизированные и узкие.** Домейн-сбои — это объединения результатов или типизированные
  `AppError`/`*Error`; не бросайте строки и не превращайте сбой хранилища в успех.
- **Защищённые переходы.** Всё, что можно нажать дважды (голос, решение, использование приглашения),
  защищено в хранилище и возвращает false/«уже сделано» при проигранной гонке. Вызывающий пропускает
  свои сайд-эффекты.
- **Пуш, а не опрос.** Состояние, нужное плагину, приходит вызовом `PluginPushPort`. Доставка —
  fire-and-forget; отключённый сервер заново получает состояние при переподключении.

### Связка

Соберите модуль в `backend/src/app.ts` (корень композиции) с его реальными репозиториями и портами,
запустите его циклы и добавьте его `stop()` в порядок выключения. Если он владеет сообщениями в проводе,
регистрируйте обработчики из `handlers/wiring.ts`; если владеет экранами/колбэками бота — регистрируйте на
единственном существующем экземпляре бота: второй `Bot` молча выбрасывает обработчики другой стороны.

### Текст

Два канала, разделённые по формату, а не по удобству:

- **plain text** (рассылки в личку, сообщения в группу, тосты) — `backend/src/services/i18n.ts`. У каждой
  записи есть `ru` и `en`; `satisfies` делает пропущенную колонку ошибкой компиляции.
- **html-экраны** (карточки в личном чате, клавиатуры) — `backend/src/i18n/locales/ru.json` +
  `en.json`, рендерятся через `bot/ui/screens`.

`backend/tests/i18n-parity.test.ts` проверяет паритет ключей, дрейф плейсхолдеров, тон, реестр эмодзи и
капитализацию в обоих слоях. Добавляйте обе локали, не одну.

### Тесты

- **Unit** — сервис против in-memory фейков в `backend/tests/helpers/in-memory.ts` и `FixedClock`. Время
  двигается через `clock.advance(ms)`, никогда через сон.
- **Real Mongo** — поведение индексов/уникальности/TTL против `mongodb-memory-server` (или
  `MONGODB_TEST_URI`) через `tests/helpers/mongo.ts`; аккуратно пропускаются, когда mongod недоступен.
- **Wire** — прогон реальных кадров `ServerConnection` через `tests/helpers/ws-harness.ts` (подписанные
  конверты, окно повторов, проверки ACK/ERROR).
- **Bot** — скриптовый харнесс диалогов для сценариев анкеты/удаления/привязки.

Модуль готов, когда его порты, mongo-реализация, сервис, клей обработчиков/бота, строки i18n и тесты
согласованы — и `bun run typecheck` вместе с `bun test` зелёные.

# Аутентификация

**Языки:** [English](../authentication.md) | Русский

Вход проходит без пароля и всегда через Telegram. Игрового пароля нет, `/login` и `/register` нет.
Каждую сессию — включая переподключение после сетевого сбоя — владелец аккаунта подтверждает одним
нажатием.

## Почему без пароля

- Аккаунт Telegram занять сложнее, чем ник в Minecraft.
- Пароль не может утечь с игрового сервера, потому что его не существует.
- Подтверждение — осознанное действие человека, поэтому одни только украденные токены сессии атакующего
  внутрь не пустят.
- Сценарий одинаков при каждом входе, а значит правило остаётся простым и проверяемым.

## Проверки при входе

Когда игрок подключается, плагин последовательно выясняет:

1. Существует ли аккаунт для этого UUID?
2. Разрешён ли доступ (нет бана, приостановки, ожидания удаления)?
3. Привязан ли аккаунт Telegram?
4. Есть ли живая сессия, с которой нужно что-то сделать?
5. Не заблокирован ли аккаунт по другой причине?
6. Требует ли этот вход подтверждения?

Только если всё прошло, плагин создаёт сессию и запускает запрос авторизации. Иначе игрок попадает в
гостевой режим или получает отказ.

## Сценарий подтверждения

```text
player joins
   -> plugin sends PLAYER_JOINED
   -> backend validates account status
   -> backend creates the session (its own session id) and an auth request:
        - one-time token, stored as a hash
        - 60-90 second TTL
        - bound to this exact session id
        - previous pending requests for the account cancelled
   -> bot sends the confirmation card:

        SERVER AUTHENTICATION

        Player: bejiihiu
        Server: Survival S2

        A new game session was detected.

        Confirm the login.

        [Confirm login] [Reject]

   -> owner taps Confirm
   -> backend verifies telegram id, uuid, session id, expiry
   -> request status -> APPROVED
   -> AUTH_APPROVED sent to the plugin (session id echoed back)
   -> plugin validates the event, hops to the player's EntityScheduler,
      restores normal gameplay
```

Отказ — или бездействие до истечения токена — оставляет сессию заблокированной; игрок остаётся в
гостевом режиме.

## Защитные меры

Сценарий защищён в глубину:

- **Одноразовые токены.** Подтверждение доказывает ровно одну сессию и ровно один раз.
- **Хранение хешей.** В базе лежат хеши токенов, никогда сами токены.
- **Короткий срок жизни.** 60–90 секунд; просроченный запрос мёртв ещё до открытия.
- **Привязка к сессии.** Токен подтверждает конкретный id сессии — одобрение старого запроса не может
  авторизовать новую сессию.
- **Single-flight.** Новый запрос авторизации отменяет предыдущий ожидающий для того же аккаунта.
- **Ограничение частоты.** Создание запросов авторизации троттлится по аккаунту.
- **Идемпотентность колбэков.** Повторные колбэки подтверждения не срабатывают дважды и не воскрешают
  истёкший запрос.
- **Отмена при отключении.** Уход игрока немедленно отменяет ожидающий запрос.
- **Никаких одобрений через другие сессии.** Backend проверяет, что одобряемая сессия — та самая, что
  запросила подтверждение.

## Поведение при отказах

- **Telegram недоступен** → входы не одобряются автоматически. Сессия остаётся заблокированной, пока
  Telegram снова не ответит. Отказ по умолчанию (fail closed) выбран сознательно.
- **Backend недоступен** → то же самое: новых одобрений нет, автоматических выдач нет. Уже
  авторизованным игрокам короткий простой не мешает; гостевые сессии продолжают работать локально.
- **Переподключения** → разорванная и заново установленная игровая сессия — это новый запрос
  авторизации, который проходит все те же проверки.

## Модель личности

- Первичный ключ аккаунта Minecraft — его **UUID**: ники меняются, UUID нет.
- У каждого игрока ровно один привязанный Telegram ID, и один аккаунт Telegram не может обслуживать
  несколько аккаунтов Minecraft.
- Привязка создаётся один раз, через сценарий приёма, и в этот момент сверяется с живой сессией на
  сервере.

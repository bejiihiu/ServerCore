# Чеклист релиза

**Языки:** [English](../release-checklist.md) | Русский

Как режется релиз, что CI о нём доказывает и как проверить опубликованные артефакты, прежде чем кто-то
их поставит. Если сборка оказалась неверной, [раздел про откат](#6-когда-ассет-неверный) — единственный
правильный выход; прочитайте его до того, как ставить тег.

## 1. Тег — это версия

Семантической версии нет, и `v1.0.0` не встречается нигде. Сборка идентифицируется так:

```text
build-<commitCount>-<shortSha>
```

— число коммитов, достижимых от помеченного коммита, и первые семь символов SHA этого коммита. Тег
вшивается в jar (`paper-plugin.yml` → `version:`), в оба имени файлов артефактов, и именно его сравнивает
апдейтер внутри плагина. Сортировка идёт только по `commitCount`; SHA идентифицирует коммит и разбивает
ничьи для отображения, но никогда — для решения об обновлении.

Два следствия, из которых вытекает всё остальное:

- **Опубликованный тег неизменяем.** Перенос или переиспользование тега либо врёт про коммит (CI это
  отклоняет), либо оставляет тот же `commitCount` (установленные серверы никогда не увидят сборку как
  более новую).
- **Исправление — это новый коммит, а не новая загрузка.** Перепубликация того же коммита даёт ту же
  версию.

## 2. Перед тегом

- [ ] Вы на `main`, всё актуально и чисто: `git fetch --tags && git pull --ff-only && git status` —
      устаревший клон посчитает `commitCount`, который CI отклонит.
- [ ] CI на `main` зелёный (сборка и тесты плагина, typecheck и тесты backend).
- [ ] `CHANGELOG.md` в разделе `[Unreleased]` описывает заметные изменения — GitHub генерирует заметки
      релиза из коммитов, а changelog — вычитанный список, который читают операторы.
- [ ] У каждого видимого пользователю изменения обновлена документация (таблицы в `docs/` и
      `README.md`).
- [ ] Никаких локальных поднятий версии: `gradle.properties` остаётся на версии разработки, релизная
      сборка переопределяет её через `-Pversion=<tag>`.

Необязательный локальный сухой прогон того же артефакта, который отдаст CI:

```bash
./gradlew :plugin:build --no-daemon -Pversion="build-$(git rev-list --count HEAD)-$(git rev-parse --short=7 HEAD)"
```

## 3. Режем релиз

```bash
count="$(git rev-list --count HEAD)"
sha="$(git rev-parse --short=7 HEAD)"
git tag "build-${count}-${sha}"
git push origin "build-${count}-${sha}"
```

Пуш тега `build-*` — это триггер релиза. Больше ничего не публикует.

## 4. Что проверяет CI

`.github/workflows/release.yml`, по порядку. Любой сбой останавливает процесс до того, как релиз
существует.

| Шаг | Отказывается продолжать, когда |
|---|---|
| Тег соответствует коммиту | тег не `build-<n>-<sha>`, либо `<n>` / `<sha>` не описывают запушенный коммит (ошибка печатает тег, который надо было использовать) |
| Сборка плагина | `:plugin:build` падает с `-Pversion=<tag>` |
| Проверки backend | падают `bun install --frozen-lockfile`, `bun run typecheck` или `bun test` |
| Подготовка артефактов | `plugin/build/libs/*.jar` — это не ровно один jar (второй jar ломает копирование) |
| Подготовка jar | сборка не создала `ServerCore-<tag>.jar` |
| Упаковка backend | тарбол собран из `package.json bun.lock tsconfig.json src tests .env.example Dockerfile .dockerignore`, с исключёнными `node_modules` и `.env` |
| Проверка подготовленного jar | jar «тонкий» (нет `kz/bejiihiu/servercore/libs/kotlin/collections/CollectionsKt.class`) или `paper-plugin.yml` не несёт ровно `version: <tag>` |
| Генерация чек-сумм | `sha256sum --text *.jar *.tar.gz > SHA256SUMS.txt` — голые имена файлов, разделитель из двух пробелов, без префикса `./` |
| Публикация | ожидаемого артефакта нет в загрузке (`fail_on_unmatched_files`) |

Чего CI **не** доказывает: что shaded jar загружается на реальном сервере Folia, что backend
действительно стартует и что чек-суммы парсятся так же, как их парсит апдейтер. Для этого и нужен
верификатор ниже, а он запускается после публикации — единственного места, где существуют настоящие URL
и имена артефактов.

## 5. Проверяем опубликованный релиз

```bash
# latest release
deploy/verify-release.sh

# a specific build
deploy/verify-release.sh build-194-dc8a896

# keep the downloaded assets (they are removed otherwise)
deploy/verify-release.sh build-194-dc8a896 --keep
```

Требования: `bash`, авторизованный `gh`, `unzip`, `tar` и `sha256sum` (или `shasum` / `openssl`). Других
зависимостей нет. `SERVERCORE_REPO=owner/name` наводит его на форк; `NO_COLOR=1` отключает цвета.

Коды выхода: `0` — все проверки прошли, `1` — минимум одна упала, `2` — проблема использования или
окружения (неверная форма тега, нет инструмента).

Он скачивает три артефакта во временную папку и печатает по строке на проверку:

| Раздел | Строки | Что значит FAIL |
|---|---|---|
| assets | jar, тарбол backend и `SHA256SUMS.txt` есть в релизе | релиз неполон — апдейтер пропускает релиз без jar |
| checksums | каждая строка — `<64 hex>  <bare name>`; SHA-256 jar и тарбола совпадают | байты в релизе — не те байты, что были зачек-суммированы; такой jar апдейтер не принимает |
| plugin jar | `paper-plugin.yml` присутствует и парсится, `version:` равен тегу, `folia-supported: true`, `packetevents` — серверная зависимость с `required: true`, kotlin stdlib зашейдена под `kz/bejiihiu/servercore/libs/kotlin`, нет top-level `kotlin/` | опубликован не тот jar, или сломался shading/relocation; в любом случае сервер не загрузит его чисто |
| backend bundle | `src/app.ts`, `package.json`, `Dockerfile` на месте; нет `node_modules`; нет `.env` | бандл нельзя запустить оператору, или он утёк настоящим env-файлом |

Строки с дайджестами используют правило самого апдейтера: разрезать строку по пробельным символам,
требовать 64-символьный hex-хеш и сравнивать имя файла с именем артефакта символ в символ (без учёта
регистра). Поэтому префикс `./name` или бинарный маркер `*name` читаются как «записи нет», и обновление
отклоняется. Строка формата намеренно строже: пайплайн пишет `<hash><two spaces><bare name>`, так что
всё иное означает, что файл правили руками после того, как `sha256sum` его создал.

## 6. Когда ассет неверный

Не анонсируйте, не «чините на месте». Разберитесь, затем откатите и перережьте.

| Симптом | Вероятная причина | Действие |
|---|---|---|
| несовпадение `sha-256` | артефакт заменён после публикации, или чек-суммы сгенерированы до финального переименования | откат, выяснить, как загрузка разошлась со сборкой |
| `version:` ≠ тег | загружен собранный локально или более старый jar; подготовленный jar был не от CI | откат, фикс workflow, перерезка |
| thin jar / `no top-level kotlin/` | изменилась конфигурация shading или relocation | откат, фикс конфигурации Gradle, перерезка |
| провалились `no node_modules` / `no .env` | потеряны исключения в tar | **сначала ротируйте каждый секрет, который был в утёкшем `.env`**, потом откат и перерезка |
| лишний jar в релизе | второй артефакт загрузили руками | апдейтер берёт первый `*.jar`, который увидит; удалите релиз и перережьте |

### Откат

1. **Удалите релиз и его тег.** Ещё ничего не установлено? На этом откат закончен.

   ```bash
   gh release delete build-<n>-<sha> --yes --cleanup-tag
   ```

   `--cleanup-tag` удаляет тег и на удалённом репозитории. Без него удалите тег явно:
   `git tag -d build-<n>-<sha> && git push origin :refs/tags/build-<n>-<sha>`.

2. **Исправьте причину новым коммитом на `main`.** Никогда не `git tag -f` и никогда не force-push
   `main`, чтобы переиспользовать старый счётчик коммитов: сборка, сохранившая свой `commitCount`, не
   «новее» ни для одного установленного сервера, так что фикс никогда не подхватится.

3. **Перережьте с нового коммита** (раздел 3). Счётчик коммитов растёт, поэтому сборка-замена
   сортируется выше сломанной.

4. **Перепроверьте** через `deploy/verify-release.sh <new-tag>` и только затем анонсируйте.

Удалённый релиз никого не откатывает вниз. Серверы, уже поставившие плохую сборку, продолжают её
крутить, пока не появится больший счётчик коммитов, поэтому настоящий путь восстановления — сборка
вперёд; удаление лишь останавливает новые установки. Если плохой релиз утёк секретом, ротируйте его
независимо от того, что сейчас говорит страница релиза.

## 7. После релиза

- [ ] `deploy/verify-release.sh` выходит с `0` на новом теге.
- [ ] На странице релиза ровно три артефакта и сгенерированные заметки.
- [ ] Операторам указывают на страницу релиза, никогда — на сборку из исходников.
- [ ] Установленные серверы: апдейтер опрашивает раз в 30 минут, ставит только строго больший счётчик
      коммитов, сверяет jar с `SHA256SUMS.txt` и держит последние три jar в
      `plugins/ServerCore/.backup/`.

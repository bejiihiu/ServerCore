# Безопасность

**Языки:** [English](../security.md) | Русский

Безопасность — это ограничение дизайна, а не поздняя надстройка. Эта страница описывает модель угроз,
правила работы с токенами и подход к защите команд.

## Модель угроз

| Угроза | Что противопоставлено |
|---|---|
| Читерские клиенты (ESP, overlay'и в духе x-ray) | Видимость сущностей отдельно для каждого наблюдателя: скрытые или замаскированные представления, синтетические атрибуты, серверная проверка прямой видимости |
| Украденная сессия Minecraft или чужой аккаунт | Каждый вход требует живого подтверждения в Telegram; игрового секрета, который можно украсть, просто нет |
| Несколько Telegram-аккаунтов на игрока | Один Telegram ID ↔ один UUID; дублирующая привязка отклоняется |
| Манипуляция голосованием | Один голос на UUID, зафиксированный список голосующих, вето на собственную заявку, сохранение каждого голоса |
| Повтор сообщений WebSocket | Окна timestamp + трекинг nonce + HMAC-подписи |
| Поддельные сообщения плагина/backend | HMAC-секрет на каждый сервер; неподписанные или устаревшие сообщения отбрасываются |
| Повышение прав в игре | OP не используется вовсе; проверки прав через LuckPerms; опасные команды заблокированы для всех игровых аккаунтов |
| Злоупотребление геймодом | Несанкционированные смены геймода откатываются в Survival; исключения выводятся из внутреннего состояния ServerCore, а не из статуса OP |
| Утечка секретов | В репозитории и логах секретов нет; конфигурация только через переменные окружения; плейсхолдеры во всех примерах |
| Потеря данных при падении/рестарте | Постоянное состояние в MongoDB; надёжная очередь исходящих для неотправленных событий; снапшоты переживают рестарты |
| Молчаливый захват во время простоя | Fail closed: нет backend — нет одобрений |

## Работа с токенами

- Все токены **одноразовые** и привязаны ровно к одной сессии.
- Хранятся только **хеши** (`auth_requests.tokenHash`); токен в открытом виде никогда не попадает ни в
  базу, ни в логи.
- Токены входа живут **60–90 секунд**; истёкший запрос нельзя воскресить повторным колбэком.
- Временные записи используют **TTL-индексы** в MongoDB, так что истёкшие артефакты исчезают без ручной
  чистки. Основные записи — аккаунты, голоса, аудит — по TTL не истекают никогда; retention-sweep
  трогает только голоса по давно решённым заявкам и тупиковые заявки, и то по куда более длинному
  графику.
- Коды привязки в deep-ссылках тоже одноразовые; использованный код мёртв.
- В логах нет ни секретов, ни токенов, ни полных персональных данных.

## Безопасность WebSocket-канала

- WSS/TLS обязателен; подключается плагин.
- Аутентификация на хендшейке происходит **до апгрейда**: плагин подписывает `server|ts|nonce` своим
  серверным секретом в запросе апгрейда, и backend проверяет подпись — вместе с окном повторов и
  проверкой сожжённого nonce — ещё до того, как сокет существует.
- Каждый кадр в обе стороны подписан HMAC отдельно, по своему каноническому json; неподписанные или
  устаревшие кадры отбрасываются.
- Id конвертов отслеживаются по кадрам; дубликаты повторно подтверждаются, но никогда не обрабатываются
  заново, поэтому потерянный ack не превращается в двойное исполнение.
- Тело каждого сообщения проходит валидацию схемы на рантайме на принимающей стороне; невалидные кадры
  отбрасываются, а не интерпретируются.
- Размер кадра ограничен (`WS_MAX_PACKET_BYTES`); слишком большой ввод отклоняется до парсинга.

## Подход к защите команд

Цель: ни один игровой аккаунт, включая помеченный как оператор, не может изменить состояние сервера или
мира административными командами.

- **Базовый чёрный список** для каждого игрового аккаунта: `/op`, `/deop`, `/fill`, `/clone`,
  `/setblock`, `/summon`, `/gamemode`, `/tp`, `/teleport`, `/give`, `/item`, `/execute`, `/effect`,
  `/attribute`, `/kill`, `/difficulty`, `/time`, `/weather`, `/gamerule`, `/worldborder`, `/stop`,
  `/reload`.
- **Алиасы и пространства имён тоже блокируются** — матчер разворачивает каждое заблокированное имя по
  живому дереву команд, поэтому одно имя закрывает всю группу алиасов, а префиксы пространств имён
  (`minecraft:tp`) соответствуют той же команде.
- **Пути датапаков запрещены** — `/function`, `/schedule` и `/datapack` заблокированы тоже, потому что
  функция датапака может нести внутри любую заблокированную команду.
- **Tab-дополнение вычищается** — заблокированные команды убраны из клиентского списка команд; это только
  отображение, а применяется запрет в момент выполнения.
- **Командные блоки под аудитом** — загруженные чанки периодически сканируются на командные блоки с
  запрещённой командой (для блоков события выполнения не существует); находки логируются и могут быть
  обезврежены на месте.
- **Альтернативные источники под аудитом:** команды, зарегистрированные плагинами, командные блоки,
  функции датапаков, RCON, консоль и вызовы через API других плагинов. Консоль — единственный
  доверенный административный канал.
- **Принудительный геймод:** Survival — единственный режим для игроков. Creative, Adventure или
  Spectator вне санкционированных сценариев (гостевой режим, `/spec`, явно разрешённые системные
  состояния) откатываются. Санкционированные состояния отслеживает внутренняя машина состояний
  ServerCore — сам факт OP ничего не решает.
- **Один `PlayerCommandPreprocessEvent` не считается защитой** — команду могут вызвать через другие
  плагины или механизмы. Блокировка лежит слоями на уровне источника команды.

## Права

- OP — не механизм администрирования; игровые аккаунты не несут статуса оператора.
- Права приходят из LuckPerms с минимальными выдачами: `servercore.admin`, `servercore.spec`,
  `servercore.spec.other`, `servercore.guest.manage`, `servercore.account.manage`.
- Каждая административная операция — особенно сессии наблюдения и удаления аккаунтов — пишется в
  `audit_logs`, доступ к этому логу ограничен.
- Скрытое наблюдение невидимо для наблюдаемого игрока, но **никогда не невидимо для аудит-трейла**.

## Честность anti-ESP

Маскировка на уровне сущностей не обещает абсолютной невидимости:

- Звуки, частицы, изменения блоков, открытие дверей и контейнеров выдают присутствие.
- Сторонние клиенты могут выводить больше, чем ванильный.
- Система существенно поднимает цену wallhack'а; она не заявляет о невозможности.

## Безопасное удаление

Удаление аккаунта — это последовательность, а не одна кнопка:

1. Личность повторно подтверждается в Telegram.
2. UUID блокируется для новых сессий.
3. Активная сессия завершается.
4. Участник удаляется из Telegram-группы; неиспользованные приглашения отзываются.
5. Привязка Telegram ↔ Minecraft отзывается.
6. Персональные данные удаляются или анонимизируются по политике хранения.
7. Записывается обезличенная запись аудита.

Запись аккаунта не удаляется, пока не завершён каждый шаг отзыва доступа.

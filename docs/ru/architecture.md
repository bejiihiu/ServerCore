# Архитектура

**Языки:** [English](../architecture.md) | Русский

ServerCore состоит из двух независимых приложений, которые не делят между собой ничего на уровне кода:

1. **Backend** — Bun + TypeScript. Владеет Telegram-ботом, всей бизнес-логикой, которой не нужен доступ к
   Minecraft API, и MongoDB.
2. **Плагин Minecraft** — Kotlin на Java 25, работает внутри сервера Folia. Владеет всем, что касается
   игрового мира.

Общаются они ровно по одному каналу: защищённое исходящее WebSocket-соединение, которое открывает плагин.
HTTP API между половинами нет — экземпляр Fastify на backend отдаёт только `/health` и никогда не
обслуживает трафик плагина.

Пошаговые рецепты, расширяющие этот дизайн, — в разделе [Расширение](extending.md).

## Обзор системы

```text
                 TELEGRAM
                    |
                grammY bot
                    |
             Bun backend (Fastify /health + native WS gateway)
                    |
          application services
                    |
                 Mongoose
                    |
                 MongoDB
                    |
                 WebSocket  (WSS, HMAC-signed, replay-protected)
                    |
             Minecraft plugin
                    |
           +---------+---------+
           |                   |
       Folia API         PacketEvents
           |                   |
           +---------+---------+
                    |
                 Minecraft
                    |
              FlectonePulse
```

## Backend

Backend — это мозг. Он владеет:

- Telegram-ботом (grammY): меню, управление аккаунтом, анкеты, голосования, подтверждения входа,
  уведомления, удаление аккаунта. Один экземпляр бота несёт все сценарии — маршруты аккаунта, приём
  (анкета/голосование/приглашения) и колбэки авторизации.
- Реестром аккаунтов: связка Minecraft UUID ↔ Telegram ID с проверками уникальности и целостности.
- Конвейером приёма: заявки, трёхчасовые голосования сообщества, проверка кворума, приглашения в группу.
- Аутентификацией: одноразовые токены (хранятся в виде хешей), короткие окна жизни, привязка к сессии.
- Администрированием Telegram-группы: одноразовые приглашения, подтверждение вступления, удаление при
  удалении аккаунта.
- Хранилищем: все постоянные коллекции в MongoDB.
- Историей событий, историей сессий, аудит-логом, уведомлениями, чистками по retention.
- Раздачей канонической локали: backend владеет эталонным бандлом `ru` и при подключении отправляет
  полный файл каждому плагину.
- Наблюдением за серверами: живое состояние каждого сервера из `SERVER_STATUS`/`SERVER_HEARTBEAT`,
  детект офлайна с алертами админам и админская команда бота `/stats`.

Его HTTP-сервер (Fastify) отдаёт только `/health`. Весь трафик плагина идёт через WebSocket-шлюз —
отдельный нативный листенер, который Fastify не касается вовсе.

Сам он игрой никогда не управляет. Когда нужно изменить состояние игры, backend отправляет
провалидированную команду по WebSocket, а плагин выполняет её в правильном контексте Folia.

Рантайм-стек: Bun, TypeScript (strict), Fastify, grammY, Mongoose, Zod, Pino. Валидация каждой входящей
структуры на рантайме идёт через Zod.

## Плагин

Плагин — исполнитель и игровая сторона с полномочиями. Код разложен по узким пакетам:

| Модуль | Ответственность |
|---|---|
| `guest` | Проверки личности при входе, гостевые сессии и лимиты сессий, ограничения взаимодействий, снапшоты позиции и их восстановление, локальный фолбэк аккаунта |
| `packet` | Ядро интеграции с PacketEvents: листенер пакетов сущностей, per-viewer хранилища состояния вида, потоки пакетов и работа с совместимостью |
| `esp` | Движок anti-ESP: пространственная сетка, регионобезопасный raytracer, решения видимости на пару (наблюдатель, цель) с кешированием |
| `disguise` | Синтетические маски мобов для скрытых игроков, отдельные для каждого наблюдателя: выбор профиля, рендеринг через PacketEvents, Folia-безопасное планирование |
| `sync` | Синхронизация состояния пакетов: реконсилер, исполнители ресинка, трекинг личности, инвалидация — держит клиентское состояние вида в согласии с серверной истиной |
| `spec` | Стек скрытого наблюдения: команда `/spec`, реестр и координатор сессий, политика прав (уровни группы или отдельная нода), скрытый наблюдатель, аудит-трейл, журнал восстановления |
| `spectator` | Инструментарий наблюдения под `/spec`: просмотр инвентаря цели в реальном времени только для чтения (с троттлингом и периодическим полным ресинком), фильтрация трейсов, скрытие наблюдателя, применение состояния вида |
| `protection` | Защита команд (матчер заблокированных команд с разворачиванием алиасов по живому дереву команд), гард геймода и сверки дрейфа, локдаун OP, аудит командных блоков, админские команды `/servercore` |
| `integration` | LuckPerms (источник прав, со статическим фолбэком из конфига, если его нет), FlectonePulse (поиск наказаний, подавление telegram-анонсов) |
| `placeholderapi` | Расширение `%servercore_…%`, работающее из кеша состояния в памяти, который наполняют события WebSocket и жизненный цикл игроков |
| `locale` | Хранилище и сервис локали; принимает целые файлы в кадрах `LOCALE_PUSH` и отвечает `LOCALE_ACK` |
| `ops` | Самообновление из GitHub releases, плановые рестарты, рестарты через панель Pterodactyl, корректное выключение с предупреждением игроков, трансляция состояния жизненного цикла сервера |
| `websocket` | Клиент шлюза: кодек протокола, политика переподключения, дедуп входящих, надёжная очередь исходящих |
| `ui` | Общий UI-тулкит: отсчёты, голограммы, темы, плейсхолдеры |
| `boot`, `config`, `player`, `util` | Связка bootstrap и команд, загрузка конфига, heartbeat присутствия, общие утилиты |

В плагине нет ни вызовов Telegram API, ни Mongoose, ни логики голосований.

## Модель потоков — регионализация Folia

Плагин исходит из того, что **главного потока не существует**. Каждая операция уходит в планировщик,
которому принадлежит затрагиваемый ресурс:

| Операция | Механизм |
|---|---|
| Работа с конкретным игроком | `EntityScheduler` |
| Работа с конкретной точкой/чанком | `RegionScheduler` |
| Глобальные операции сервера | `GlobalRegionScheduler` |
| Фоновые периодические задачи | `AsyncScheduler` |
| Блокирующий I/O (файлы, обработчики WebSocket) | Виртуальные потоки (Java 25) |

Жёсткие правила, которых придерживается код:

- Колбэки WebSocket никогда не трогают `Player`, `World`, `Entity` или `Inventory` напрямую. Путь всегда
  такой: *получить → провалидировать → разрешить UUID → перейти в планировщик-владелец → выполнить*.
- Изменяемые объекты Bukkit не хранятся в глобальных коллекциях; конкурентное состояние живёт в
  конкурентных структурах, никогда в обычной `HashMap`.
- На региональных потоках нет ни блокирующего I/O, ни тяжёлой обработки пакетов.
- Задачи, привязанные к сущности, отменяются при её удалении.
- Виртуальные потоки масштабируют только фоновый I/O — это никогда не обход региональной модели Folia.

Метаданные плагина объявляют `folia-supported: true`. Это декларация-контракт, по которому аудируют
реализацию, а не флаг сборки.

## Потоки данных

### Вход нового игрока (первый раз)

```text
Minecraft join
   -> plugin checks registry (local cache, no sync DB call)
   -> no account -> guest session created
   -> original state snapshotted (world, coords, angles, gamemode, speeds)
   -> player moved to Spectator, interactions disabled
   -> personal one-time deep link posted in chat
   -> player opens Telegram -> /start <linking code>
   -> backend verifies ownership of the Minecraft session
   -> preliminary Telegram <-> UUID link created
   -> application flow unlocked
```

### Вход авторизованного игрока

```text
Minecraft join
   -> plugin sends PLAYER_JOINED
   -> backend validates account status (ACTIVE, not banned/suspended)
   -> backend creates the session (its own session id) and an auth request:
        one-time token (hashed, 60-90 s TTL), bound to that session id
   -> bot asks the owner: confirm / deny
   -> confirmation -> AUTH_APPROVED over WebSocket (session id echoed back)
   -> plugin validates the event, hops to EntityScheduler
   -> player restored to normal gameplay
```

### Голосование по заявке

```text
Application submitted (Telegram, step-by-step form)
   -> backend starts vote, 3 h window
   -> eligible-voter count frozen at start
   -> members vote via inline keyboard (one vote per UUID)
   -> expiry: quorum >= 50 % of eligible AND > 50 % of valid votes in favour
   -> approved -> single-use group invite -> join event confirms membership
   -> rejected/expired -> player notified, 3-month reapplication lock
```

### Вычисление anti-ESP

```text
Player movement / periodic tick (budgeted rate)
   -> spatial index selects nearby candidates per viewer
   -> server-side line-of-sight check (block geometry, eye positions,
      distance, sneaking state)
   -> per (viewer, target) pair state resolved:
        VISIBLE  - real entity representation
        DISGUISED - synthetic entity, synthetic equipment/attributes
        HIDDEN   - no representation at all
   -> PacketEvents applies the per-viewer packet changes
   -> results cached with controlled refresh; invalidated on
      world change, respawn, teleport, gamemode or equipment change
```

### Падение backend

```text
WebSocket drops
   -> reconnect with exponential backoff
   -> new logins are NOT auto-approved (fail closed)
   -> already-authenticated players keep playing
   -> guest sessions keep working locally
   -> uncancellable events queue in a durable outbox
   -> on reconnect, state is reconciled and queued events replayed
```

## Модель хранения

MongoDB — единственное постоянное хранилище на стороне backend. Основные коллекции:

| Коллекция | Назначение |
|---|---|
| `users` | Аккаунты: личность Minecraft, привязка Telegram, статус жизненного цикла |
| `applications` | Заявки на приём и их метаданные голосования |
| `application_drafts` | Состояние незавершённой анкеты, чтобы брошенный диалог можно было продолжить |
| `votes` | Отдельные голоса (уникальность по заявке + голосующему) |
| `voting_messages` | Живая карточка голосования в группе — нужна для обновления результатов |
| `sessions` | Сессии игроков со статусом жизненного цикла |
| `auth_requests` | Ожидающие и завершённые подтверждения входа (хеши токенов, TTL-индекс) |
| `telegram_links` | Связка Telegram ↔ Minecraft |
| `guest_snapshots` | Исходное состояние игрока, снятое перед гостевым режимом |
| `group_invites` | Артефакты одноразовых приглашений и состояние их использования |
| `audit_logs` | Административные действия, сессии наблюдения, удаления |
| `server_events` | Сырой поток событий от плагина |
| `conversation_states` | Хранилище диалогов grammY (на Mongo) |
| `punishments_external` | Только чтение поверх внешнего источника наказаний; своего наказательного движка ServerCore не создаёт |

Временные данные (запросы авторизации, истёкшие артефакты) живут на TTL-индексах. Аккаунты, голоса и
записи аудита по TTL не истекают никогда.

Помимо TTL, мёртвые строки раз в сутки подчищает retention-sweep: закрытые сессии (60 дней), осиротевшие
гостевые снапшоты, карточки голосований и голоса по заявкам, решённым более 90 дней назад, отозванные или
истёкшие неиспользованные приглашения в группу (30 дней, использованные — через год) и отклонённые или
истёкшие заявки старше года. Аккаунты, одобренные заявки и записи аудита остаются.

### Когда MongoDB недоступна

Сбои Atlas M0 — ожидаемое явление, поэтому backend устроен так, чтобы жить без базы:

- **Старт не зависит от базы.** Листенеры (Fastify `/health`, WS-шлюз) поднимаются, пока драйвер
  переподключается в фоне с экспоненциальной задержкой — от 1 с с удвоением до потолка в 30 с. `/health`
  отвечает `503 {"status":"degraded","mongoConnected":false}`, пока соединения нет, и `200`, когда оно
  появилось. SIGTERM во время цикла ретраев останавливает его сразу, а не держит процесс открытым.
- **Входы остаются fail-closed.** Вход, который не может прочитать или записать хранилище, отклоняется на
  границе модуля, логируется и никогда не одобряется — игрок просто остаётся гостем. Пуши backend→плагин
  (приглашение и вердикт авторизации, link-токен) паркуются в очереди сервиса и уходят на следующем свипе,
  когда и связь, и база снова живы; пуши, провисевшие дольше 10 минут, отбрасываются, а следующий вход
  заново синхронизирует состояние.
- **Кадр никогда не стоит сокета.** Кадр от плагина подтверждается по получении (`ACK`), и только потом
  обрабатывается. Если обработке нужна база и запись не удалась, backend логирует это и отвечает на тот же
  ack кадром `ERROR { code: "HANDLER_FAILED", inReplyTo: <frame id> }` по тому же соединению: без
  закрытия, без зависания, следующие кадры идут дальше. На стороне backend повторов упавшего кадра нет —
  этим владеет плагин: коррелированный `ERROR` возвращает воспроизводимый кадр в очередь и переотправляет
  его ограниченное число раз с новым id конверта, поэтому обработчики обязаны переживать повторную
  обработку одного и того же события. Служебные записи, которые по замыслу best-effort (аудит-трейл spec),
  логируются и проглатываются, а не роняют кадр.
- **Записи, которые могли бы подвесить игрока, компенсируются.** Отправка заявки, упавшая между сменой
  статуса (`UNREGISTERED → VOTING`) и вставкой заявки, откатывает статус, так что сбой стоит черновика
  (его придётся заполнить заново), а не оставляет аккаунт в состоянии, из которого ничего не выходит.
- **Уборка не наслаивается.** Свипер авторизаций и суточный retention несут guard от
  реентерабельности: тик, пришедший посреди прохода, пропускается, а упавший проход снимает guard и
  сохраняет расписание. Упавшая цель чистки считается нулём и никогда не блокирует остальные.

Плагин держит рядом с конфигом свои небольшие надёжные файлы: гостевые снапшоты
(`guest.snapshot-storage-path`), durable-очередь кадров жизненного цикла гостей и локальный аудит-трейл
spec (`spec.audit.*`). Они существуют, чтобы плагин переживал собственные рестарты и падения backend, не
превращая игровой сервер во вторую базу данных.

## Производительность

- WebSocket-пуш вместо опроса; никаких периодических чтений MongoDB на каждого игрока.
- Локальные кеши состояния аккаунтов и авторизации с контролируемой свежестью.
- Anti-ESP использует пространственное разбиение, кеш на пары и проверки с ограничением частоты — никогда
  O(n²) на каждый тик.
- Некритичные события батчатся; у очередей ограниченная память.
- Расширения PlaceholderAPI читают только кеш и никогда не делают синхронных запросов к базе.
